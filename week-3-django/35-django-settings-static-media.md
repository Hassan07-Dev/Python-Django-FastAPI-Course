## PHP/Laravel bridge

You already know this whole problem space; only the file names change. Laravel splits config across `config/*.php` files and reads secrets from a `.env` file via `env()` and `config()`. Django crams the equivalent into a single `settings.py` (a plain Python module — it's *code*, not declarative config), and the community uses **`django-environ`** to get Laravel-style `env('KEY')` behavior. Laravel's `APP_DEBUG` is Django's `DEBUG`; `APP_KEY` is `SECRET_KEY`; the `database.php` connection array is the `DATABASES` dict; and `config/app.php`'s `providers` array is roughly `INSTALLED_APPS`. Laravel's `public/` directory and `asset()`/`mix()`/`vite()` helpers map onto Django's static-files machinery, and Laravel's `storage/app/public` + `php artisan storage:link` is exactly Django's **media files** concept. Even the deploy gotcha is shared: just as you'd never ship Laravel with `APP_DEBUG=true`, you never ship Django with `DEBUG=True`.

| Laravel | Django |
|---|---|
| `config/*.php` files | `settings.py` (one module, or split package) |
| `.env` + `env('KEY')` | environment vars + `django-environ`'s `env('KEY')` |
| `APP_DEBUG` | `DEBUG` |
| `APP_KEY` | `SECRET_KEY` |
| `config('database.connections.pgsql')` | `DATABASES['default']` |
| `config/app.php` providers | `INSTALLED_APPS` |
| HTTP middleware kernel | `MIDDLEWARE` |
| `public/` assets + `vite()` | static files (`collectstatic` → `STATIC_ROOT`) |
| `storage/app/public` + `storage:link` | media files (`MEDIA_ROOT` / `MEDIA_URL`) |
| `php artisan about` / deploy checks | `python manage.py check --deploy` |

## Core concept: `settings.py` is just Python

The single most important thing to internalize: **`settings.py` is a normal Python module that runs top to bottom once at startup**. There is no special DSL. Anything Python can do — `if` statements, list operations, `os.environ`, importing other modules — is fair game. Django simply imports this module and reads its uppercase module-level names. That's the entire contract.

```python
# settings.py — Django reads UPPERCASE names from this module after import.
from pathlib import Path

# BASE_DIR is the project root. Path(__file__) is .../myproject/settings.py,
# so two .parent hops climb to the directory that holds manage.py.
BASE_DIR = Path(__file__).resolve().parent.parent
# => PosixPath('/home/you/myproject')
```

Which module Django uses is controlled by the `DJANGO_SETTINGS_MODULE` environment variable (set in `manage.py` and `wsgi.py`/`asgi.py`). This is the hook that makes split settings possible — point it at `myproject.settings.prod` and you get production config.

### The settings that matter, one by one

```python
# ─── SECURITY ────────────────────────────────────────────────────────────────

# SECRET_KEY signs sessions, password-reset tokens, signed cookies, CSRF, etc.
# If it leaks, an attacker can forge these. NEVER hardcode it in real projects.
SECRET_KEY = "django-insecure-CHANGE-ME"  # placeholder generated by startproject

# DEBUG must be False in production. When True, Django returns a full stack
# trace + your settings on errors — a goldmine for attackers. It also disables
# template caching and serves static files via the dev server.
DEBUG = True

# ALLOWED_HOSTS is the guest list of Host headers Django will answer to.
# With DEBUG=False and an empty list, EVERY request 400s. In prod you MUST
# list your domain(s). This blocks HTTP Host-header poisoning attacks.
ALLOWED_HOSTS = []  # e.g. ["api.example.com", "example.com"]


# ─── APPS ────────────────────────────────────────────────────────────────────

# INSTALLED_APPS: every app Django should load — its models, migrations,
# admin registrations, template tags, management commands. Order matters
# occasionally (e.g. an app overriding another's templates).
INSTALLED_APPS = [
    "django.contrib.admin",
    "django.contrib.auth",
    "django.contrib.contenttypes",
    "django.contrib.sessions",
    "django.contrib.messages",
    "django.contrib.staticfiles",   # <-- powers static file handling
    # third-party
    "rest_framework",
    # your apps
    "blog",
]


# ─── MIDDLEWARE ──────────────────────────────────────────────────────────────

# MIDDLEWARE is an ORDERED onion. A request travels DOWN the list to the view;
# the response travels back UP. Order is load-bearing: SecurityMiddleware first,
# auth after sessions, etc. This is Laravel's middleware kernel.
MIDDLEWARE = [
    "django.middleware.security.SecurityMiddleware",
    "django.contrib.sessions.middleware.SessionMiddleware",
    "django.middleware.common.CommonMiddleware",
    "django.middleware.csrf.CsrfViewMiddleware",
    "django.contrib.auth.middleware.AuthenticationMiddleware",
    "django.contrib.messages.middleware.MessageMiddleware",
    "django.middleware.clickjacking.XFrameOptionsMiddleware",
]


# ─── TEMPLATES ───────────────────────────────────────────────────────────────

# TEMPLATES configures the template engines. APP_DIRS=True means Django looks
# in each app's templates/ folder. 'DIRS' adds project-wide template roots.
TEMPLATES = [
    {
        "BACKEND": "django.template.backends.django.DjangoTemplates",
        "DIRS": [BASE_DIR / "templates"],  # project-level templates
        "APP_DIRS": True,                  # also search <app>/templates/
        "OPTIONS": {
            "context_processors": [
                "django.template.context_processors.debug",
                "django.template.context_processors.request",
                "django.contrib.auth.context_processors.auth",
                "django.contrib.messages.context_processors.messages",
            ],
        },
    },
]


# ─── DATABASE ────────────────────────────────────────────────────────────────

# The default from `startproject` — SQLite, a single file. Great for dev,
# wrong for production. We replace this with Postgres below.
DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.sqlite3",
        "NAME": BASE_DIR / "db.sqlite3",
    }
}


# ─── I18N / TIME ─────────────────────────────────────────────────────────────

LANGUAGE_CODE = "en-us"
TIME_ZONE = "UTC"     # store everything in UTC; convert at the edges
USE_I18N = True
USE_TZ = True         # store timezone-aware datetimes — keep this True
```

> **Why is `DEBUG=True` so dangerous in production?** Because the yellow error page Django renders on an exception leaks your traceback, local variables, installed apps, and *settings values* (Django redacts ones containing `SECRET`/`PASSWORD`, but not everything). It also means `ALLOWED_HOSTS` is effectively ignored. One forgotten `DEBUG=True` is the single most common Django security incident.

## Core concept: managing settings across environments

Your laptop, CI, staging, and production need *different* values: different databases, `DEBUG` on/off, different allowed hosts and secret keys. There are two mainstream solutions. They are not mutually exclusive — large projects often combine them.

### Pattern A — Split settings modules

Turn `settings.py` into a `settings/` **package** with a shared base and per-environment overrides.

```text
myproject/
  settings/
    __init__.py
    base.py     # everything common
    dev.py      # imports base, flips DEBUG on, sqlite, console email
    prod.py     # imports base, DEBUG off, postgres, real ALLOWED_HOSTS
    test.py     # fast hashers, in-memory db
```

```python
# settings/base.py  (the common settings.py content from above lives here)
from pathlib import Path
BASE_DIR = Path(__file__).resolve().parent.parent.parent  # note: 3 parents now
# ... INSTALLED_APPS, MIDDLEWARE, TEMPLATES, etc. ...
```

```python
# settings/dev.py
from .base import *          # noqa: F403  pull in everything

DEBUG = True
ALLOWED_HOSTS = ["localhost", "127.0.0.1"]
EMAIL_BACKEND = "django.core.mail.backends.console.EmailBackend"
```

```python
# settings/prod.py
from .base import *          # noqa: F403
import os

DEBUG = False
ALLOWED_HOSTS = os.environ["DJANGO_ALLOWED_HOSTS"].split(",")
SECRET_KEY = os.environ["DJANGO_SECRET_KEY"]   # KeyError on boot if missing — good
```

You select the module at runtime:

```bash
# Run with the prod settings module
export DJANGO_SETTINGS_MODULE=myproject.settings.prod
python manage.py runserver

# Or one-off, without exporting:
python manage.py migrate --settings=myproject.settings.dev
```

**Trade-off:** explicit and readable, but you must keep three files in sync, and any secret still has to come from somewhere (so you usually combine this with env vars anyway).

### Pattern B — One settings module, env-driven (12-factor)

Keep a single `settings.py` and pull every environment-specific value from environment variables. This is the **12-factor app** approach and what most modern Django (and all Laravel) projects do. `django-environ` makes it ergonomic and adds type casting.

```bash
pip install django-environ
```

```python
# settings.py
from pathlib import Path
import environ

BASE_DIR = Path(__file__).resolve().parent.parent

env = environ.Env(
    # define defaults + CASTS: (type, default)
    DEBUG=(bool, False),                      # default False is the safe choice
    ALLOWED_HOSTS=(list, ["localhost"]),
)

# Read a local .env file if present (dev convenience). In prod, real env vars
# are already set by your platform, so this no-ops harmlessly.
environ.Env.read_env(BASE_DIR / ".env")

SECRET_KEY = env("SECRET_KEY")               # required — raises if absent
DEBUG = env("DEBUG")                          # cast to bool: "1"/"true" -> True
ALLOWED_HOSTS = env("ALLOWED_HOSTS")          # "a.com,b.com" -> ["a.com", "b.com"]

# One line replaces the whole DATABASES dict (see next section).
DATABASES = {"default": env.db("DATABASE_URL")}
```

Your `.env` file (dev only, **git-ignored**):

```bash
# .env  — NEVER committed
SECRET_KEY=local-dev-only-key-not-the-prod-one
DEBUG=True
ALLOWED_HOSTS=localhost,127.0.0.1
DATABASE_URL=postgres://app:secret@localhost:5432/myapp
```

> `env("DEBUG")` returns a real `bool` because we declared the `bool` cast. This avoids the classic footgun where `bool("False")` is `True` (a non-empty string is truthy!). `django-environ` parses `"False"`, `"0"`, `"no"`, `"off"` as `False`.

### Never commit secrets — the rules

1. **`.env` is git-ignored.** Add it to `.gitignore` on day one.
2. **Commit a `.env.example`** with the *keys* and dummy values so teammates know what to set. (This is exactly Laravel's `.env.example`.)
3. **Production secrets come from the platform** — Docker/Kubernetes secrets, AWS Secrets Manager, systemd `EnvironmentFile`, the hosting dashboard. They are *never* in the repo.
4. **If a secret ever lands in git, it's compromised** — rotate it. Deleting the commit is not enough; it lives in history and clones.

```gitignore
# .gitignore
.env
*.sqlite3
/media/
/staticfiles/
__pycache__/
```

Generate a fresh production `SECRET_KEY`:

```bash
python -c "from django.core.management.utils import get_random_secret_key; print(get_random_secret_key())"
# => 8x@k2!p... (50 random chars) — paste into your prod secret store, not git
```

## Core concept: `DATABASES` for PostgreSQL

SQLite is fine for a first run but unsuitable for production (single-writer locking, no real concurrency, limited types). Postgres is the default professional choice. The driver is `psycopg` (psycopg 3):

```bash
pip install "psycopg[binary]"   # psycopg 3, the modern driver
```

The explicit, verbose form:

```python
DATABASES = {
    "default": {
        "ENGINE": "django.db.backends.postgresql",
        "NAME": env("DB_NAME"),
        "USER": env("DB_USER"),
        "PASSWORD": env("DB_PASSWORD"),
        "HOST": env("DB_HOST", default="localhost"),
        "PORT": env("DB_PORT", default="5432"),
        "CONN_MAX_AGE": 60,        # reuse connections for 60s (persistent conns)
        "OPTIONS": {
            "connect_timeout": 5,
        },
    }
}
```

The 12-factor form — one URL collapses all six keys, which is far easier to inject as a single env var:

```python
# DATABASE_URL=postgres://app:secret@db.internal:5432/myapp
DATABASES = {"default": env.db("DATABASE_URL")}

# Add persistent connections on top of the parsed URL:
DATABASES["default"]["CONN_MAX_AGE"] = 60
```

> **Why `CONN_MAX_AGE`?** By default Django opens a new DB connection per request and closes it after — costly under load. Setting `CONN_MAX_AGE` keeps connections alive and reused. For most apps `60` is a good start; if you put a connection pooler like PgBouncer in front, you may set it to `0` and let the pooler manage lifetimes.

## Core concept: static files vs media files — the critical distinction

This trips up *every* newcomer, so let's nail it. Both are "files served over HTTP that aren't HTML pages," but they are completely different in origin, lifecycle, and trust.

| | **Static files** | **Media files** |
|---|---|---|
| Source | Written by **you/developers** | Uploaded by **users** at runtime |
| Examples | CSS, JS, logos, fonts, favicon | Profile pictures, PDFs, attachments |
| In version control? | Yes (they're part of the code) | No (they're runtime data) |
| Lifecycle | Collected at **deploy time** | Created continuously in **production** |
| Settings | `STATIC_URL`, `STATIC_ROOT`, `STATICFILES_DIRS` | `MEDIA_URL`, `MEDIA_ROOT` |
| Trust level | Trusted (you wrote them) | **Untrusted** (validate type/size!) |
| Laravel analogue | `public/` + `vite()` assets | `storage/app/public` + `storage:link` |

The golden rule: **static = your assets, shipped with the code; media = user data, created by the running app.** Mixing them up (e.g. saving uploads into a static dir) is a classic mistake that breaks on the next deploy.

## Core concept: static files configuration

Three settings do three different jobs. Beginners conflate them constantly.

```python
# The URL prefix browsers use to request static assets.
# A template tag like {% static 'css/app.css' %} renders /static/css/app.css
STATIC_URL = "static/"

# WHERE collectstatic gathers files INTO (the single output dir for prod).
# This dir is NOT in git; your web server (or WhiteNoise) serves it.
STATIC_ROOT = BASE_DIR / "staticfiles"

# Extra source dirs collectstatic should pull FROM, beyond each app's
# own static/ folder. For project-wide assets not tied to one app.
STATICFILES_DIRS = [BASE_DIR / "static"]   # source, not output
```

Think of it as a pipeline:

```text
   SOURCES                              OUTPUT (prod)
   ───────                              ─────────────
   <app>/static/...        ┐
   STATICFILES_DIRS  ──────┼──  collectstatic  ──►  STATIC_ROOT/  ──►  served at STATIC_URL
   (admin, DRF, etc.)      ┘
```

`STATIC_ROOT` and `STATICFILES_DIRS` must be **different directories** — Django will error if `STATIC_ROOT` is also listed in `STATICFILES_DIRS`, because that would mean "collect into a folder I'm also reading from."

### What `collectstatic` does

```bash
python manage.py collectstatic
# => Copies every static file (from all apps + STATICFILES_DIRS) into STATIC_ROOT.
#    179 static files copied to '/home/you/myproject/staticfiles'.
```

In development, the `django.contrib.staticfiles` app finds your assets on the fly across all source dirs, so you never run `collectstatic` locally. In production there's no app doing live discovery — instead, **at deploy time** you run `collectstatic` once to flatten everything (your app assets *plus* the admin's and DRF's CSS/JS) into a single `STATIC_ROOT` folder that nginx or WhiteNoise can serve straight off disk.

Using a static file in a template:

```html
{% load static %}
<link rel="stylesheet" href="{% static 'css/app.css' %}">
<!-- renders: <link rel="stylesheet" href="/static/css/app.css"> -->
```

### Serving static in dev vs prod

**Dev:** `runserver` serves static automatically (via the staticfiles app) as long as `DEBUG=True`. Zero config. This convenience **does not exist** when `DEBUG=False` — set it false locally and your CSS vanishes. That's expected.

**Prod, option 1 — WhiteNoise (simplest, no nginx needed):** WhiteNoise lets Django serve its own static files efficiently with caching headers and compression. Perfect for Heroku/containers/PaaS.

```bash
pip install whitenoise
```

```python
MIDDLEWARE = [
    "django.middleware.security.SecurityMiddleware",
    "whitenoise.middleware.WhiteNoiseMiddleware",   # right AFTER security
    # ... the rest ...
]

# Compress files and add cache-busting hashes to filenames (app.a1b2c3.css)
# so you can cache forever and still invalidate on change.
STORAGES = {
    "staticfiles": {
        "BACKEND": "whitenoise.storage.CompressedManifestStaticFilesStorage",
    },
    "default": {  # media — see next section
        "BACKEND": "django.core.files.storage.FileSystemStorage",
    },
}
```

> `STORAGES` is the modern (Django 4.2+) replacement for the old `STATICFILES_STORAGE` / `DEFAULT_FILE_STORAGE` settings. Use it; the old single-value settings are deprecated.

**Prod, option 2 — nginx / CDN (highest performance):** Don't route static through Python at all. Let nginx serve `STATIC_ROOT` directly, and ideally put a CDN in front. Conceptually:

```nginx
# nginx (conceptual) — Python never touches static or media bytes.
location /static/ { alias /home/you/myproject/staticfiles/; }
location /media/  { alias /home/you/myproject/media/; }
location /        { proxy_pass http://127.0.0.1:8000; }  # gunicorn/uvicorn
```

## Core concept: media files (user uploads)

Two settings, mirroring the static ones:

```python
# URL prefix the browser uses for uploaded files.
MEDIA_URL = "media/"

# Filesystem directory where uploads are SAVED and READ from.
# NOT in git. In prod, point this at a persistent volume (or use S3).
MEDIA_ROOT = BASE_DIR / "media"
```

Wire a model field to it — `upload_to` is a subpath *under* `MEDIA_ROOT`:

```python
# models.py
from django.db import models

class Profile(models.Model):
    # avatars land in MEDIA_ROOT/avatars/<filename>; URL is MEDIA_URL + path.
    avatar = models.ImageField(upload_to="avatars/", blank=True)
    resume = models.FileField(upload_to="resumes/%Y/%m/", blank=True)  # date dirs
```

```python
# Reading the URL of an uploaded file:
profile.avatar.url    # => '/media/avatars/jane.png'
profile.avatar.path   # => '/home/you/myproject/media/avatars/jane.png'
```

`ImageField` needs Pillow:

```bash
pip install Pillow
```

**Serving media in dev** needs an explicit URL wiring (the dev server won't do it for you the way it does static):

```python
# urls.py
from django.conf import settings
from django.conf.urls.static import static
from django.urls import path

urlpatterns = [
    # ... your routes ...
]

# Only in DEBUG — in prod nginx/S3 serves /media/, never Django.
if settings.DEBUG:
    urlpatterns += static(settings.MEDIA_URL, document_root=settings.MEDIA_ROOT)
```

> **Security note:** media is **untrusted user input**. Always validate file type and size (DRF serializers or a model `validators=[...]` argument), and never trust the uploaded filename or content-type header. Serving uploaded HTML/SVG from your own domain can enable stored-XSS — serve media from a separate domain or via a storage backend with the right headers in serious apps.

## Core concept: logging configuration basics

By default, with `DEBUG=False`, uncaught exceptions are emailed to `ADMINS` and otherwise the console is quiet. You want explicit, structured logging. Django uses Python's standard `logging` via a `LOGGING` dict (`dictConfig` format).

```python
import logging  # noqa: F401  (only needed if you reference levels in code)

LOGGING = {
    "version": 1,                     # always 1
    "disable_existing_loggers": False,  # keep Django's own loggers working
    "formatters": {
        "verbose": {
            "format": "{asctime} {levelname} {name} {message}",
            "style": "{",             # use {}-style placeholders
        },
    },
    "handlers": {
        "console": {
            "class": "logging.StreamHandler",   # write to stdout/stderr
            "formatter": "verbose",
        },
    },
    "root": {                          # catch-all logger
        "handlers": ["console"],
        "level": "INFO",
    },
    "loggers": {
        "django.request": {           # 4xx/5xx request errors
            "handlers": ["console"],
            "level": "WARNING",
            "propagate": False,
        },
    },
}
```

Use it in your own code by getting a named logger — the convention is `__name__`:

```python
# views.py
import logging

logger = logging.getLogger(__name__)   # logger named after the module

def checkout(request):
    logger.info("checkout started for user %s", request.user.id)
    try:
        ...
    except PaymentError:
        logger.exception("payment failed")   # logs message + full traceback
        raise
```

> **Why log to the console (stdout) in containers?** The 12-factor rule: treat logs as an event stream. Your app writes to stdout; the platform (Docker, Kubernetes, systemd-journald) captures and ships it. Don't manage log *files* inside the app — let the infrastructure do it.

Log levels, lowest to highest: `DEBUG` < `INFO` < `WARNING` < `ERROR` < `CRITICAL`. A logger set to `INFO` emits `INFO` and above, dropping `DEBUG`.

## Core concept: the deployment checklist

Before going live, Django ships a built-in linter that audits your settings for production safety. Run it with the **production** settings active.

```bash
DJANGO_SETTINGS_MODULE=myproject.settings.prod python manage.py check --deploy
```

It flags issues like:

```text
?: (security.W004) SECURE_HSTS_SECONDS not set ...
?: (security.W008) SECURE_SSL_REDIRECT is not True ...
?: (security.W009) SECRET_KEY has less than 50 characters ...
?: (security.W018) DEBUG is True. Do not deploy with DEBUG=True.
?: (security.W012) SESSION_COOKIE_SECURE is not True ...
```

A solid production security block to silence these (and actually be safe):

```python
# Only meaningful with DEBUG=False and HTTPS terminated in front of the app.
SECURE_SSL_REDIRECT = True            # redirect http -> https
SECURE_HSTS_SECONDS = 31536000        # 1 year; tell browsers "https only"
SECURE_HSTS_INCLUDE_SUBDOMAINS = True
SECURE_HSTS_PRELOAD = True
SESSION_COOKIE_SECURE = True          # cookies only sent over https
CSRF_COOKIE_SECURE = True
SECURE_CONTENT_TYPE_NOSNIFF = True

# If behind a proxy/load balancer that terminates TLS, trust its header:
SECURE_PROXY_SSL_HEADER = ("HTTP_X_FORWARDED_PROTO", "https")
```

> `check --deploy` is the analogue of running through Laravel's deployment optimization steps and audit. Make it part of your CI pipeline so a regression (someone flips `DEBUG=True`) fails the build instead of reaching production.

## Common mistakes & gotchas

- **Leaving `DEBUG=True` in production.** The #1 Django security mistake. It leaks tracebacks and settings, and disables `ALLOWED_HOSTS`. Default it to `False` in code so you must *opt in* to debug.
- **`bool(env_var)` truthiness trap.** `bool("False")` is `True`. Always cast env booleans through `django-environ` (or compare strings explicitly). A stray `DEBUG="False"` string is `True` if not cast.
- **Committing `.env` or hardcoding `SECRET_KEY`.** Once in git history, it's compromised forever — rotate it. Git-ignore `.env` before the first commit.
- **Empty `ALLOWED_HOSTS` with `DEBUG=False`.** Every request returns 400 and you'll think the server is broken. Set your domains.
- **Confusing static and media.** Saving user uploads into a static dir, or expecting `collectstatic` to handle uploads. They're separate systems.
- **Putting `STATIC_ROOT` inside `STATICFILES_DIRS`.** Django raises `ImproperlyConfigured`. Output dir ≠ source dir.
- **Forgetting `collectstatic` on deploy.** Admin and DRF pages render unstyled because their assets were never gathered into `STATIC_ROOT`.
- **Expecting CSS in dev after setting `DEBUG=False`.** The dev server only auto-serves static when `DEBUG=True`. That's by design — use WhiteNoise locally if you must test prod-like serving.
- **Media not appearing in dev.** You forgot the `static(MEDIA_URL, ...)` line in `urls.py`. Unlike static, media is not auto-served even in DEBUG.
- **Mutable `from base import *` surprises.** When you `MIDDLEWARE = [...]` in an override file you *replace* the list; if you mean to add, do `MIDDLEWARE = [...] + MIDDLEWARE` or insert explicitly. `import *` copies the binding, but mutating the imported list mutates base's list too.
- **`MEDIA_ROOT` on ephemeral container storage.** Uploads vanish on redeploy. Use a persistent volume or, better, S3 (`django-storages`).

## Best practices

- **Default secrets and `DEBUG` to the safe value** (`DEBUG=(bool, False)`), so forgetting an env var fails closed, not open.
- **Make required secrets crash on boot.** `env("SECRET_KEY")` with no default raises immediately — far better than a server running insecurely.
- **One `DATABASE_URL`** beats six discrete DB env vars; it's atomic and matches every PaaS.
- **Use `STORAGES` (Django 4.2+)**, not the deprecated `STATICFILES_STORAGE`/`DEFAULT_FILE_STORAGE`.
- **WhiteNoise's `CompressedManifestStaticFilesStorage`** for hashed, far-future-cacheable static assets.
- **Validate every upload** (size + type) — treat media as hostile input. Consider serving it from a separate domain.
- **Log to stdout**, let the platform capture it; don't write log files from the app.
- **Run `check --deploy` in CI** with prod settings so security regressions fail the build.
- **Commit `.env.example`, never `.env`.** Keep the key list discoverable without leaking values.
- **Store datetimes in UTC** (`USE_TZ=True`, `TIME_ZONE="UTC"`) and convert at presentation.

## Interview Q&A

**Q: What does `DEBUG=True` do, and why is it dangerous in production?**
**A:** It makes Django render detailed error pages (traceback, local vars, settings) on exceptions, serve static via the dev mechanism, disable template caching, and effectively bypass `ALLOWED_HOSTS`. In production it leaks sensitive internals to attackers — it must always be `False` in prod.

**Q: What is `ALLOWED_HOSTS` for?**
**A:** It's the whitelist of `Host` header values Django will serve. With `DEBUG=False`, any request whose `Host` isn't listed gets a 400. It defends against HTTP Host-header injection/poisoning (e.g. poisoned password-reset links). In prod you list your real domains.

**Q: Explain the difference between static files and media files.**
**A:** Static files are assets you (the developer) ship with the code — CSS, JS, images — version-controlled and gathered at deploy time via `collectstatic` into `STATIC_ROOT`. Media files are user uploads created at runtime in production, stored under `MEDIA_ROOT`, never in git, and must be treated as untrusted input.

**Q: What's the difference between `STATIC_ROOT` and `STATICFILES_DIRS`?**
**A:** `STATICFILES_DIRS` lists *source* directories `collectstatic` reads *from* (project-wide assets, in addition to each app's `static/`). `STATIC_ROOT` is the single *output* directory `collectstatic` writes *into* for the web server to serve. They must be different paths.

**Q: What does `collectstatic` actually do, and when do you run it?**
**A:** It copies all static files from every app's `static/` folder plus `STATICFILES_DIRS` into `STATIC_ROOT`, flattening them so a web server can serve them directly. You run it at deploy time (and in CI/Docker builds), not during local development where the staticfiles app discovers files live.

**Q: How do you serve static files in production?**
**A:** Either WhiteNoise (Django serves them via middleware with compression and hashed filenames — great for PaaS/containers) or a real web server/CDN like nginx serving `STATIC_ROOT` directly so Python never touches the bytes. The dev server's auto-serving is for development only.

**Q: How do you keep secrets out of source control?**
**A:** Read them from environment variables (often via `django-environ`), keep a git-ignored `.env` for local dev, commit a `.env.example` with key names only, and inject real values in prod via the platform's secret store. If a secret is ever committed, rotate it — git history keeps it forever.

**Q: Split settings modules vs a single env-driven settings file — which and why?**
**A:** Split modules (`base/dev/prod`) are explicit and good when environments differ structurally. Env-driven single-file (12-factor) keeps one module and varies behavior purely through env vars — simpler to deploy and matches PaaS conventions. They combine well: a `prod.py` that still pulls secrets from env. Pick based on team/infra; env-driven is the more common default.

**Q: Why use `CONN_MAX_AGE` in `DATABASES`?**
**A:** Without it, Django opens and closes a DB connection per request, adding latency under load. `CONN_MAX_AGE` keeps connections alive for reuse (persistent connections). Set `0` if you front the DB with a pooler like PgBouncer.

**Q: What is `python manage.py check --deploy` and when do you run it?**
**A:** It's Django's built-in deployment audit that warns about insecure settings — `DEBUG=True`, weak `SECRET_KEY`, missing HSTS/SSL redirect, non-secure cookies, etc. Run it with production settings as part of CI before deploying.

**Q: How do you serve user-uploaded media in development vs production?**
**A:** In dev, add `static(settings.MEDIA_URL, document_root=settings.MEDIA_ROOT)` to `urlpatterns` under an `if settings.DEBUG` guard. In prod, never serve media through Django — nginx serves `MEDIA_ROOT`, or you use cloud storage (S3 via `django-storages`).

**Q: Why is `settings.py` "just Python," and what's one practical consequence?**
**A:** Django merely imports the module named by `DJANGO_SETTINGS_MODULE` and reads its uppercase names. Consequently you can use real Python — conditionals, list manipulation, `os.environ`, imports — which is exactly what enables split settings (`from .base import *`) and env-driven config.

## Cheat sheet

```python
# ── Core settings ───────────────────────────────────────────────
DEBUG = env("DEBUG")                # MUST be False in prod
ALLOWED_HOSTS = ["example.com"]     # required when DEBUG=False
SECRET_KEY = env("SECRET_KEY")      # never hardcode / commit
INSTALLED_APPS = [...]              # apps Django loads (models, admin, ...)
MIDDLEWARE = [...]                  # ordered request/response onion
TEMPLATES = [{...}]                 # template engine config
DATABASES = {"default": env.db("DATABASE_URL")}   # one URL, all keys

# ── Static (developer assets) ───────────────────────────────────
STATIC_URL = "static/"             # browser URL prefix
STATIC_ROOT = BASE_DIR/"staticfiles"  # collectstatic OUTPUT (prod)
STATICFILES_DIRS = [BASE_DIR/"static"]  # extra SOURCE dirs

# ── Media (user uploads) ────────────────────────────────────────
MEDIA_URL = "media/"
MEDIA_ROOT = BASE_DIR/"media"

# ── Modern storages (Django 4.2+) ───────────────────────────────
STORAGES = {
  "staticfiles": {"BACKEND": "whitenoise.storage.CompressedManifestStaticFilesStorage"},
  "default":     {"BACKEND": "django.core.files.storage.FileSystemStorage"},
}
```

```bash
# ── Commands ────────────────────────────────────────────────────
python manage.py collectstatic              # gather static -> STATIC_ROOT
python manage.py check --deploy             # prod security audit
python -c "from django.core.management.utils import get_random_secret_key as g; print(g())"
python manage.py runserver --settings=myproject.settings.dev

# ── Env var selecting settings ──────────────────────────────────
export DJANGO_SETTINGS_MODULE=myproject.settings.prod
```

| Concept | Static | Media |
|---|---|---|
| Author | developer | end user |
| In git? | yes | no |
| When created | deploy time | runtime |
| URL setting | `STATIC_URL` | `MEDIA_URL` |
| Disk setting | `STATIC_ROOT` | `MEDIA_ROOT` |
| Dev serving | auto (DEBUG) | `static()` in urls.py |
| Prod serving | WhiteNoise / nginx / CDN | nginx / S3 |

**Settings-across-environments rules:** default secrets/`DEBUG` to the *safe* value · required secrets crash on boot · `.env` git-ignored, `.env.example` committed · prod secrets from the platform · run `check --deploy` in CI.
